{% extends "base.html" %} {% load i18n %} {% comment %} The operator's administrative area — the product's own shell, with the administrative navigation in place of the product's. This file used to be a standalone layout: its own , its own sidebar, its own account menu, and a dark stone rail whose stated job was to signal "you are administering, not using". The product owner rejected that signal: the administrative screens should read as the same application as everything else, and the comparison he made was with Settings — which is also an area apart, and which does this by extending base.html and overriding ONE block. So this is now what layouts/settings.html is: eight lines of nav inside ``{% block sidebar_nav %}``, reusing ``sidebar-nav-item`` and ``sidebar-section-label`` with no colour of its own. Light sidebar, same tone, same chrome. The 239 lines it replaces were a second copy of the shell that had to be kept in agreement with base.html by hand. Kept as a layout rather than pasting these links into each of the four screens: the navigation is one list, and the four templates still say ``{% extends "layouts/admin_shell.html" %}``. It also keeps the opt-in property the standalone file was written for — a screen joins the administrative area by extending this, and nothing else inherits this nav by accident. What base.html shows an account with no workspace is handled in base.html itself, by ``{% if request.workspace %}`` / ``request.org`` conditions that are true of ANY workspace-less session rather than rules about the admin area. See the comments there. Nothing here is an access control: every view under this layout is decorated with ``_staff_required`` (apps/billing/views.py).
