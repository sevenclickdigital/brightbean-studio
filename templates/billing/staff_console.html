{% extends "layouts/admin_shell.html" %} {% load i18n billing_extras %} {% comment %} Customers: one table row per account, with every action behind a modal. A table, not the cards this used to be. Each account was a card tall enough to hold two always-open forms, so two accounts filled the screen and fifty were unreadable — the complaint that produced this shape. The question the page answers is comparative ("who pays, who is exempt, who is filling the disk"), and comparing means reading down a column. One row per ORGANIZATION, not per workspace: the account is what gets charged, comped, edited and signed in as. A workspace-grained table would repeat the same account on consecutive lines and leave the operator unsure which row a button belonged to. Per-workspace detail (status, disk, the per-workspace comp toggle) lives in the row's modal, which is where it is unambiguous. The modal is opened on demand and holds all five actions, so nothing on this page can be fired by accident while scrolling, and the forms are only in the DOM when the operator asked for them. Alpine, matching the rest of the project's modals. Every action is a POST with a CSRF token. There is not one GET link among them: a GET reset would let an embedded image mail a customer a reset link, and a GET deactivation would let any page an operator visits switch a customer off. Extends layouts/admin_shell.html, which is base.html with the administrative navigation in place of the product's — the same arrangement layouts/settings.html uses. Extending base.html directly would bring Publish, Create Idea and the connected-channels list along, all pointing at a workspace an operator account does not have. Access is ``is_staff`` (see apps/billing/views._is_billing_staff), so nothing here is reachable by a customer, and nothing at all by an impersonated session. {% endcomment %} {% block title %}{% translate "Customers" %} - {% translate "Administration" %} - Brightbean{% endblock %} {% block page_header %}
