{% extends "layouts/admin_shell.html" %} {% load i18n billing_extras %} {% comment %} Subscriptions: one row per contract, plus what the provider has told us. Why a fourth screen rather than more of the other three. Customers is per ACCOUNT — the comparative view, with the actions on it. Plan and prices is per FIGURE and counts states in aggregate ("2 awaiting the first payment"), which is exactly useless for finding WHICH two. This one is per WorkspaceSubscription, and per gateway event, which is the grain the product owner asked for and the only grain at which "is this particular contract paying" is answerable. The line this screen holds, and the reason it says so three times: CONTRACTED IS NOT RECEIVED. The recurring figure is the sum of what active subscriptions are priced at — money we have agreed to bill. What has actually been collected is knowable only from the provider, and with no Asaas credentials nothing has been. Printing the first number under a heading like "revenue" would be the one mistake here worse than printing no number. Amounts in the event table come from the provider's own payload and are labelled as such. A missing amount renders as an em dash, never as R$ 0,00 and never as our own list price dressed up as a confirmation — see views._event_amount_cents for exactly which field is trusted. Read-only. Every action on a subscription already lives on Customers, and a second place to comp a workspace is a second rule to keep in agreement with the first. {% endcomment %} {% block title %}{% translate "Subscriptions" %} - {% translate "Administration" %} - Brightbean{% endblock %} {% block page_header %}
