BrightBean Studio - Style Guide

Reference for the tokens and UI patterns the app actually ships. Everything below is copied from the code; when they disagree, the code wins and this file should be updated.

Source of truth
  • theme/static_src/src/styles.css: all design tokens (:root) and shared component classes. Built with Tailwind CSS v4 (@import "tailwindcss") to theme/static/css/dist/styles.css.
  • templates/base.html: app shell (sidebar, main panel, flash messages, htmx error toast, create-workspace modal).
  • templates/components/ui_select.html: dropdown select. templates/approvals/partials/_toasts.html: toast host. templates/approvals/partials/_status_badge.html + apps/approvals/templatetags/approval_extras.py (STATUS_META): editorial status pills.
  • theme/static_src/tailwind.config.js is not loaded. Tailwind v4 ignores it unless @config is set, and styles.css doesn't set it. Its brand.primary (indigo #4f46e5) colors are dead config.

White-label architecture

There are three token layers in styles.css: brand (--brand-*, --brand-font-*), then semantic (--primary*, --surface-*, --text-*), then component classes (.btn-brand, .sidebar-nav-item.active, ...).

How branding works today: tokens are static. Nothing injects --brand-* or --primary at runtime: no context processor and no inline <style> in base.html. To rebrand, you edit the --brand-* values in styles.css and rebuild the CSS.
Per-tenant fields that exist: Workspace.primary_color / secondary_color (hex, apps/workspaces/models.py). Only primary_color is read, and only as the workspace dot colour in the cross-workspace calendar (falls back to #F97316). Organization.logo_url shows in the client portal header (templates/client_portal/portal_base.html). Neither one changes the app's tokens.

Rebrand = change only this block, then npm run build in theme/static_src

--brand-50 … --brand-900     /* orange scale; --primary = 500, hover = 600, soft = 50, muted = 100, ring = 200 */
--brand-green-100/200/500/600 /* selection controls: checkbox accent, toggle on-state */
--brand-font-display / --brand-font-body / --brand-font-mono

Buttons

The four classes in styles.css are .btn-brand, .btn-outline, .btn-link and .btn-social. All are full width by default (except .btn-link) and pill-shaped. In-app secondary, neutral and danger buttons are plain Tailwind utilities.

Cascade caveat: the component classes in styles.css are unlayered, but Tailwind v4 utilities live in @layer utilities, so the component rules win. In markup like class="btn-brand px-4 py-2 text-sm" (about 15 places), the utilities don't override .btn-brand's padding, font-size or width:100%. Check in the browser before you rely on those overrides.

Token ↔ Tailwind mapping

No custom Tailwind theme is active, so there are no bg-brand-* classes. Templates use the token through style="…var(--primary)" or a default Tailwind class with the same value. Only the token form rebrands.

Known gaps in the code

These are inconsistencies found while writing this guide. They are listed so that nobody copies them.

IssueWhere
The brand orange is hardcoded far more often than tokenised: ~518 *-orange-* utilities, 63 #F97316 literals in 27 files, and ~29 rgba(249,115,22,…) (including .btn-brand:hover and .btn-primary-lift:hover in styles.css, and .auth-bg). Editing --brand-* alone does not rebrand the app.templates/**, styles.css
var(--brand-primary) is used but never defined, so the icon and button render with no colour.client_portal/magic_link_confirm.html
--primary-rgb and --error-600 are referenced only with fallbacks and are never defined, so the fallbacks (always orange or red) are what renders.styles.css (.btn-primary-tint, .btn-error-darker), base.html, composer/create_landing.html
tailwind.config.js declares brand.primary/secondary (indigo/violet) but is not loaded by Tailwind v4.theme/static_src/tailwind.config.js
The login page overrides .btn-brand with #93a240 / #849139, which is close to, but not equal to, --brand-green-500 #94A43F / -600 #7B8A33.templates/account/login.html
The status pills hardcode hex values, including brand orange for Pending/Changes Requested and violet #7C3AED (not in the palette) for Hold. The connection badge uses Tailwind green/yellow instead of the status tokens.approval_extras.py STATUS_META, social_accounts/_status_badge.html
The flash messages in base.html use bg-*-50 text-*-800 rather than .alert-* (-700 tokens), so there are two visual styles for the same message.templates/base.html
Some checkboxes use accent-orange-500, others .bb-checkbox (green). ui_select uses text-orange-500 focus:ring-orange-400, which has no effect without the forms plugin.base.html, composer/create_landing.html, components/ui_select.html
.pi-* platform colors, .cal-filter-select and .a-card are re-declared in page <style> blocks instead of living in styles.css.calendar.html, cross_calendar.html, composer/compose.html, analytics/index.html
--ease-spring, --dur-slow, and .focus-ring are defined but unused.styles.css
The component classes are unlayered, so Tailwind utilities on the same element (btn-brand px-4 py-2) don't apply. See Buttons.styles.css

Guidelines

✓Reference tokens (var(--primary), bg-(--primary)) for anything brand-coloured, not orange-* or #F97316.
✓Use the shared classes before inventing new ones: .form-input-styled, .bb-select, .bb-toggle, .bb-checkbox, .btn-brand, .alert-*, {% status_badge %}, {% ui_select %}, and the showToast event.
✓Keep status meaning on the fixed palette (success/warning/error/info). Selection controls use bean green.
✓Neutrals are stone (warm). Don't introduce gray-*/slate-*.
✕Don't use the display serif in buttons, labels, nav or form fields.
✕Don't add web fonts or a Tailwind config theme. Tokens live in styles.css :root.
